4. JOBS AND REVISED HTTP CONTRACTS
Separate durable job status from patient status, model findings and human cases.
All expensive actions use jobs. POST /events, POST /events/{id}/outreach and
POST /inbound return 202 {job_id, resource_id, state, status_url, duplicate} after
durable acceptance. They do not wait for a Bedrock result. Include pagination
and consistent machine-readable error responses. GET /jobs/{job_id} returns
authorized progress/result links. Preserve useful existing read-route names.
Read routes include event board, patient thread, patient-scoped simulator
messages, escalation queue, audit and operations/cost summaries.
Human routes include confirm event, assign case, acknowledge case and resolve
case with notes and expected version. API derives tenant and actor from validated
identity, never from an unchecked body field. Protect jobs and metrics too.
Only GET /health is publicly readable, with no sensitive configuration.
POST /admin/reset and demo clock/fault tools require demo environment + admin.
Do not expose a shared x-admin-token or secrets through VITE_* variables.
Publish request/response examples before frontend feature work begins.

Use a versioned job envelope like:
{schema_version:1, job_id, kind, tenant_id, event_id, event_version,
 patient_id:null, source_message_id:null, created_at, deadline_at,
 correlation_id, payload_ref}.
Queue IDs/references rather than full patient conversations. Validate all fields.
Job states are ACCEPTED, QUEUED, RUNNING, SUCCEEDED, HUMAN_REVIEW, FAILED_VISIBLE
or CANCELLED. Define valid transitions, lease expiry and terminal outcomes.
Store individual attempts separately. Queue depth is an AWS metric, not a job
state. Explain eventual consistency and measured metric timestamps in the UI.

5. DURABILITY: ATOMIC INTAKE AND TRANSACTIONAL OUTBOX
Use DynamoDB transactions to commit the inbound record, stable job identity,
audit decision and outbox record atomically. Only then return 202.
For a keyword emergency, include the escalation record/evidence and urgent
notification outbox in that transaction, without waiting for the model.
Reject invalid or unauthorized inputs before acceptance. On transaction failure,
return a retryable error; do not show 'accepted'. Bind idempotency to authenticated
tenant/source/message ID and a payload digest. Same ID/same payload returns the
existing result; same ID/different payload returns 409. Hashing text and minute
is not an acceptable identity. Retain deduplication records for the documented
queue/redrive replay window; do not rely only on a transaction client token.

A filtered Work/Outbox stream dispatches committed intents to triage, outreach
or urgent notification queues. Publish before marking dispatched. A crash in
that gap may duplicate delivery: consumers must handle it. Implement retryable
dispatch, an index of pending outbox items, periodic reconciliation and alarms.
Stream retention is finite; pending durable outbox work must be discoverable
without a full table scan after stream failures or retention expiry.
Never claim a database write followed by an SQS call is atomic.

6. WORKERS, RETRIES AND CORRECTNESS
Use separate triage, outreach and urgent notification processing lanes so bulk
outreach does not monopolize ingress or alert delivery. Start with small batches
and conservative concurrency; protect API capacity within actual account quotas.
Use SQS ReportBatchItemFailures, DLQs and maxReceiveCount >= 5. Set visibility
timeout >= 6 x function timeout + batching window. Bound function duration.
Persist checkpoints/results so notification retries do not rerun successful AI.
Use conditional job leases with fencing/version checks, expiry and safe recovery.
Duplicate jobs must not increment completed counters or create cases twice.
Use idempotent transactions for job completion, state, audit and follow-on outbox.
Bound total model attempts across SDK retries and SQS redeliveries; do not let
each retry layer multiply the model budget. Prefer disabling hidden SDK retries
and implementing at most two explicitly metered, durably tracked attempts per
job, unless a documented alternative provides the same bound. Failures retry with
bounded jitter/backoff. Invalid model output, refusal or exhausted attempts goes
to visible human review. DLQ work has an operator alert, replay procedure and
reconciliation into FAILED_VISIBLE; it must not disappear from workload accounting.
SNS/email is at-least-once at the external side-effect boundary. Use stable alert
IDs and tracked publish attempts; do not promise exactly-once email delivery.
Publishing an email is not human acknowledgment.

7. DATA ACCESS AND SCALE
Reuse original patient/event/message fields where useful; add tenant, event
version, timestamps, source message identity and validated schema versions.
Choose a small, documented table design: Records for profiles/events/status/
messages, Escalations, append-oriented Audit, Work/Outbox with stream, and Control
for usage/rate counters is an acceptable baseline. Explain every key and index.
Partition by tenant and access pattern. Index patients by tenant/geography;
distribute hot event status/audit workloads across fixed shards. Document shard
queries, aggregation and pagination, including GSIs. Never scan all patients per
outage or return every patient to render one board page. Do not maintain one hot
counter per outage without discussing contention; use idempotent sharded counts
or a justified measured demo simplification. Batch matching and fan-out with
continuation jobs rather than a minute-long agent loop over the whole registry.
Outage cancellation/version changes invalidate stale outreach work. Protect
patient state from out-of-order model completions using version/sequence checks.
An older safe reply must never downgrade a newer unresolved emergency.

8. DETERMINISTIC RULES AND HUMAN WORK
Document risk weights as editable demo assumptions, not clinical rules. Show
inputs and reasons. Missing duration, unknown backup, ambiguous areas and dates
require visible uncertainty and confirmation; do not invent a restoration time.
ZIP matching is approximate geography and must be labeled as such.
Patient state and escalation state are separate. Opening a case creates a stable
case identity per defined incident, supports later evidence/severity updates and
cannot silently overwrite a resolved case. Define when a new case is required.
Only authorized human coordinators may acknowledge or resolve; resolution needs
notes and optimistic concurrency. Patient replies/AI cannot resolve a case.
Use explicit handling for unknowns: no defaulting unknown device-running to true,
unknown emergency to false, or unknown remaining battery to zero without a flag.
Do not infer a requested supply from an absent backup tank alone.
Use multilingual keyword checks before AI as a conservative extra layer, with
tests for negation, quotes, indirect phrasing, typos and prompt attacks. They are
not complete emergency detection. Any earlier critical finding stays active when
the Guardrail blocks or the model fails. Explicit reply codes are acknowledgments
and requests for help, not automatic clinical clearance of existing risk/cases.
Uncertainty and model unavailability lead to human review. Keep case assignment,
unacknowledged age and owner workload visible. Follow-up times are configurable
demo policy, with urgent-risk overrides, not universal medical deadlines.
Track message queued/sent/failed/acknowledged separately from patient safety.
Connectivity failure becomes unreachable/human outreach; do not claim offline
delivery or guaranteed reachability during a cellular outage.

9. AI CONTRACT AND GUARDRAILS
Mandatory live Bedrock jobs: notice extraction and multilingual free-text reply
triage. Use canonical Pydantic schemas with null/unknown values and bounds.
Triage returns only supported findings: patient_reported_safe yes/no/unknown,
emergency yes/no/unknown, device_running true/false/null, backup_hours_left
number/null, explicitly stated needs, translation, exact evidence quotes and
model confidence. Confidence is model-reported and uncalibrated, not a clinical
probability. Validate quotes occur in original text; this checks provenance, not
truth or full semantic entailment. Keep the original available to authorized staff.
Never treat patient content as instructions, interpolate it into system policy,
or allow it to select tenant, permissions, tools or actor identity.
Check the exact selected model's structured-output/forced-tool support with a
small live call. If unavailable, use a documented schema-constrained fallback
with strict validation and one bounded repair; route remaining failure to human
review. Do not silently switch to a model with untested language/safety behavior.
Apply the versioned Guardrail where supported and explicitly validate/screen
serialized tool arguments/results where required. Guardrails do not automatically
screen every tool-use field and do not sanitize original invocation logs.
Block treatment/dosing/device-setting advice while allowing reports of distress
to be captured and escalated. Test both. A blocked model output never discards
the incoming message. Keep model usage/latency/guardrail metadata for evidence.
If a Strands outreach planner is added later, scope it to at most 5 patients per
job, approved tools and a bounded step budget. It may recommend/draft; validated
code enqueues actions. It has no resolve, raw database, arbitrary HTTP or shell
tool. Start core outreach with approved language templates and deterministic
personalization so AI outages do not prevent initial check-ins.

10. AUTHENTICATION, AUTHORIZATION AND PRIVACY
Use Cognito/OIDC with PKCE for the SPA and HTTP API JWT authorizers for staff
routes. Validate issuer/audience/expiry and appropriate access-token scopes.
Map staff to trusted tenant membership and roles server-side; do not trust a
self-supplied tenant claim. Use coordinator, viewer and demo_admin roles.
Never embed a client secret in the SPA. Simulator requests use short-lived,
server-issued patient/event-scoped credentials validated by the backend or a
dedicated authorizer. Token exposure must not grant staff read or resolve access.
Prevent URL/referrer/log leakage; do not use patient IDs as authentication.
Real provider callbacks, if added later, require verified signatures/replay
handling and sender-to-patient mapping, not an arbitrary patient_id body.
Enforce tenant/patient/role checks on every object route including job progress,
audit, metrics, resolve, reset and export. Use stable 401/403/404 conventions and
prevent existence leaks. Test horizontal and vertical privilege escalation.
Encrypt storage/queues, use TLS, and grant least-privilege resource-scoped roles.
Application audit writers cannot update/delete audit entries; retention/TTL and
admin abilities mean this is not automatically a tamper-proof legal record.
Use minimal PHI-free SNS subjects/bodies with authenticated case links.
Do not log conversation text, bearer tokens, auth headers or guardrail traces
with detected PII. Minimize/redact identifiers before model calls; preserve
original messages only in authorized application storage. Synthetic invocation
logging may be enabled for the demo, clearly labeled. Guardrails are not log
redaction. CORS is not access control. HTTP API has no direct AWS WAF attachment;
document a supported future placement or REST alternative if WAF is requested.

11. QUOTAS AND COST ENFORCEMENT
Check actual account/model/Region quotas; distinguish customers, request rate,
concurrency, tokens/minute, guardrail limits and provider messaging throughput.
Do not claim 'serverless means unlimited'. More APIs in one account/Region do
not multiply its shared gateway quota; queues do not recover rejected requests.
Implement shared request/token admission limits across workers with atomic
control counters; local per-process counters alone are insufficient. Reserve
conservative model quota/budget before a call, including model-specific output
token accounting, and record actual usage separately. Give reply triage priority
over optional AI work; urgent deterministic escalation must not require AI quota.
Use configurable caps: MAX_MODEL_CALLS_PER_RUN, MAX_INPUT_SIZE, MAX_OUTPUT_TOKENS,
MAX_MODEL_ATTEMPTS_PER_JOB, MAX_AGENT_STEPS, queue concurrency and tenant/run
usage ceilings. Default load-test AI cap to 5 calls; larger live tests are explicit.
Count retries/repairs in caps. Describe a conservative spend bound; do not claim
the entire AWS account has a guaranteed dollar cap or Budget alerts stop spend.
Pricing must be a dated config by Region/model, with source URLs and units.
Unknown rates stay unknown; never fabricate a precise total. Itemize model tokens,
Guardrail policies/text units, API, Lambda, DynamoDB including transactions/GSIs,
SQS, schedules, logs/hosting and optional messaging segments/fees. Mark credits
and taxes separately. Label estimates versus observed usage versus billed costs.
No per-patient custom CloudWatch dimensions and no unbounded prompt/log retention.

12. FRONTEND AND OPERATIONS
Make a clear board with outage confirmation, ranked/paginated patients, outreach
progress, patient thread, exact-evidence highlights and separate escalation queue.
Use text/icons with colors, accessible focus and readable recording typography.
Add assignment, acknowledgment, resolution notes, timestamps, loading/error/empty
states, pending triage and human-review states. Retry buttons reuse idempotency
keys for the same operation; a new message receives a new ID.
Staff dashboards may poll authorized aggregates at a modest interval with backoff
and stop when hidden/idle. Simulator polling is for the few demo windows only.
Do not design millions of phones to poll every two seconds. Document production
provider webhooks and possible staff push updates as the next stage.
Include a capacity worksheet for a hypothetical 1 million registered patients,
100,000 affected patients and 20,000 free-text replies over 10 minutes. Separate
registry size, internal fan-out, ingress rate, model RPM/TPM, worker concurrency,
queue-drain time and staff capacity. Use measured service times and actual quotas
when available; otherwise label assumptions and show the limiting factor. Treat
this as a capacity model, not a claim that a million-patient load test was run.
Operations panel: accepted unique jobs, pending/running, succeeded, human review,
failed-visible, cancelled, duplicate submissions, queue age/depth, DLQ, intake
and completion latency, unresolved/unacknowledged cases, model calls/tokens and
estimated cost, each with source and time window. Keep tenant information scoped.
Make counters reconcilable with durable records; never invent a zero-failure badge.
All pages show SYNTHETIC DEMO DATA and distinguish LIVE BEDROCK, MOCK and REPLAY.

13. OBSERVABILITY AND RECOVERY
Use structured logs with correlation/job IDs and non-sensitive error codes.
Create alarms for pending-outbox age, oldest queue message, DLQ, Lambda errors/
throttles, API errors, model throttling and unacknowledged urgent cases. No alarm
should depend solely on the same optional AI path that failed.
Implement scheduled follow-up/reconciliation queries against a due-time index.
Do not use DynamoDB TTL deletion as a precise timer. Timer actions re-check
reply/case/event state and contact attempt before acting; stale timers do nothing.
Document SNS subscription confirmation, redrive, replay, rollback, resource
cleanup and whether work survives a deployment. Demo clock/fault injection uses
injected clock/provider adapters, requires demo_admin and cannot affect live data.
Document remaining single-Region, cellular/provider and human-staffing limits.

14. ACCEPTANCE AND EVIDENCE
Write focused tests for high-impact invariants and integration boundaries, not
tests that only mirror implementation. Cover duplicate/reordered/concurrent
messages, idempotency payload conflict, transaction failure, crash after queue
publish, expired job lease, dispatch outage, retries, DLQ/reconciliation, model
timeout/invalid JSON/refusal, stale event cancellation, budget exhaustion and
cross-tenant/role violations. Distinguish unit/integration/stub/live-AWS evidence.
Use 60 synthetic patients in EN/ES/VI/ZH/TL, two synthetic agencies, ambiguous
notices and at least one uncertain time. No real people or medical records.
Preserve the original 30 labeled reply evaluation cases including 6 emergencies,
6 ambiguous replies and 2 injections. Add safety regressions separately; report
recall with counts, false positives, human-review rate and language-specific
misses. Never turn a hand-written demo set into a clinical validation claim.
Create a rate-controlled script defaulting to a small test. It must distinguish
real Bedrock, deterministic replies, mock/replay and synthetic transport. A
1,000-submission demonstration is optional after measured small tests and caps.
Verify every unique accepted job is in exactly one current state; do not double
count DLQ and job state. At drain, no unaccounted pending/running jobs remain.
Prove no duplicate case records from replay, and urgent keyword cases become
visible without waiting for Bedrock. Record intake p50/p95 separately from
model completion and human acknowledgment. Performance numbers are measured
results or explicit targets, never made-up achievements.
